# Target and migration: Group Settings since 94-resumable

## Design before compatibility constraints

The operator deploys a reusable setup at defined events. The station owns intended state and the headset owns evidence of effect. Resolve one effective immutable version per device at contact; live notifications speed reconciliation when assignments change. Retain one draft per setup. A deployment commits the exact affected scope; if the scope changed after confirmation, ask for a new confirmation. Release means stop managing, leaving system values in place.

The independent exercise was given the operator and platform constraints before any existing architecture or source. The agent reported no prior exposure and did not inspect code or historical docs. It proposed exclusive membership with optimistic concurrency, reusable immutable versions, separately recorded submissions/results, a local apply worker and locally owned Wi-Fi recovery. The parent had prior exposure. The proposal's fixed version per group, history, and queued operations were considered as alternatives below; these add behavior beyond the current requests. It raised A → B → A and offline cache freshness as ambiguities; the project decisions confirm once per version per boot and explicit offline use of the last received version.

| Product model | Benefit | Fit to verified requirements |
| --- | --- | --- |
| Shared setup with a latest active publication, resolved by assignment and applied at specific events | One change for multiple groups. Offline devices converge at contact without a delivery queue. | Chosen. Preserves local edits between application events and does not require superseding old offline jobs. |
| Fixed rollout with immutable version pinned per group, and an operation/result for each target | Good for canaries, waves, approval, historical auditing and tracking a fixed cohort. | Group pinning changes shared publication semantics. A queue needs supersession after reassignments and does not replace the device attempt journal. No such rollout requirement is recorded. |
| Continuous desired-state enforcement | Corrects drift and reasserts a kiosk policy without operator action. | Overwrites intentional local edits and can repeat effects after an uncertain attempt. Conflicts with the apply and Retry contract. |

| Boundary | Greenfield preference | Reconciliation and route |
| --- | --- | --- |
| Station configuration | One transaction owns groups, exclusive device membership, assignments, draft and publication. Stable group IDs and an owner precondition on edits. A small local DB is reasonable for a new data model. | Current JSON already has save-then-publish semantics and a single committed configuration reference. Keep it. Stable IDs and SQLite would improve rename/recreate identity and write scope but require migration and rollback work. The earlier 256-device probe measured write volume only; there is no current production storage bottleneck measurement or multiple-writer requirement. |
| Membership writes | Store only additions/removals that represent operator intent and verify the touched owners at commit. Leave unrelated changes in place. | Replace the current console's full-list move at its command boundary. Reuse group storage and snapshots. Keep old no-move operations for older callers. A renamed source conflicts conservatively. Same-name delete/recreate (identity ABA) remains a name-keyed limitation. |
| Delivery and Retry | Send effective state at contact and after relevant committed changes. Bind explicit Retry to an exact device/version; do not materialize per-device copies on the station. | Current canonical connection and send gate already implement this boundary. Keep; preserve old device versions and summary-only redaction. |
| Headset | One apply worker owns durable boot/version/Retry claims; record readbacks before delegating the Wi-Fi stage. A distinct last-received cache enables the explicit local action. | Keep the process worker, private journal and cache, and firmware adapter. Do not imply the offline cache is current server intent. Automatically retrying or requiring online confirmation for local Reapply would change the product. An unreadable journal stays fenced; if persistent storage cannot record a newer cache/clear, offline freshness cannot be guaranteed. |
| Network recovery | A local Wi-Fi operation owns its baseline, deadline and exact result; the package worker consumes its evidence. Startup owns its bounded wait. | Keep the current journals and operation-ID correlation. A joint journal would couple Wi-Fi recovery to package parsing/storage and complicate older APKs. Station reachability is not evidence of a fresh usable Wi-Fi association. |
| Operator projection | Editor owns draft and staged edits; station owns committed assignment and publication. Show device observations only for the selected revision. | Preserve the November 10 combined routes, exact scope checks, and consolidated UI. An editor submission acknowledgment does not prove device application. Firmware/catalog exceptions need targeted decisions, not new architecture. |
| Legacy device commands and release | Keep jobs, identity, APK delivery and self-update separate from package execution. | Keep both build flavors and existing platform paths. Replacing the station and client together would add mixed-version and PICO release verification cost without measured improvement. |

The effective flow is: edit intent → validate against committed scope → persist a new desired snapshot → publish it to the console → resolve latest policy for each affected current connection → durably claim on the headset → read back scalar effects → let local Wi-Fi recovery settle → report the exact version. The headset can run the explicit Reapply from its last received version independently of the server; it cannot infer a later server change while offline.

## Compare membership migration methods

| Route | What changes | Decision |
| --- | --- | --- |
| Keep full-list move and refresh faster | Reduces the common stale window but cannot close the gap between snapshot and Save. | Reject for the modern member editor. |
| Compare-and-swap on the entire roster | Detects any concurrent roster change. Even independent additions and moves conflict and need manual replay. It still needs a versioned command to avoid silent fallback on older stations. | Consider if the business needs to replace a cohort as a single action. |
| Submit a scoped edit with expected owners | Applies independent edits without moving or releasing untouched devices. The server rejects the whole edit if a touched owner changed. The same durable commit and delivery path is reused. | Selected and verified in isolation before application. |
| Replace storage, protocol and Android stack | Can add stable identities and a history of operations but brings new migrations, mixed-version behavior and real-device parity requirements. | Defer until a requirement or measured bottleneck justifies it. |

The candidate uses `UPDATE_GROUP_MEMBERS` with `name`, `add` mapping IDs to the expected source name or null, and `remove` listing IDs expected to belong to the edited group. It uses a distinct command so an older station cannot treat the payload as a full-list move. The console waits for the server to advertise `membership_edits`. The server sends the committed group snapshot and save acknowledgment before attempting policy delivery. It attempts delivery even if the console disconnects. The original `SET_GROUP_MEMBERS` compatibility path retains list replacement without cross-group moves. The storage format and device protocol stay compatible. Server and console should be upgraded or rolled back together.

Verification compares the original and candidate console/WS paths with matched synthetic input, checks the persistence and offline delivery cases, and keeps the Android and deployment paths covered by current parity evidence. The result and residual limits are in [VERIFY.md](VERIFY.md).
